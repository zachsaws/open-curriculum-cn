# V3.7 规划 — 知识图谱数据完整度 + 产品化收尾

**起点 (V3.6.10c)**: 1906 概念 / 14 学科, LLM 增强后 description/assessment/real_examples/common_mistakes/teaching_activity/content_req/src_page 全部 100% 覆盖, 但 key_points 65.8% / academic_req 13.8% / teaching_voice 0% (UI 复用 description).

**目标 (V3.7)**: 把数据完整度从 67% 拉到 99%+, 同时给"教学话术"独立字段, 让数据经得起任何用户视角审查.

## P0 — 补 academic_req + key_points 完整度 (1-2 天)

**为什么 P0**: 这两个字段是 V3.3.5 LLM 增强时**漏写**的, 覆盖率 13.8% / 65.8%. academic_req 1643 概念没填, 1 个数据就能让"为什么 9 按钮" / "打印版" 完美闭环.

**目标**:
- academic_req: 13.8% → 100% (1643 概念补完)
- key_points ≥3 条: 65.8% → 100% (651 概念补到 3 条)

**方法**:
- 1 次 LLM call 同时生成 academic_req + key_points (省 token)
- 14 学科**串行** 1 个 bg task 1 个学科 (避免 token plan 撞墙, 之前 V3.3.1 教训)
- 学科顺序按"小→大" 优先, 让快速反馈先来:
  1. pe_health (87) — 1.5h
  2. biology (71) — 1h
  3. chemistry (62) — 1h
  4. art (78) — 1.5h
  5. labor (85) — 1.5h
  6. geography (91) — 1.5h
  7. info_tech (97) — 2h
  8. science (121) — 2.5h
  9. physics (121) — 2.5h
  10. history (136) — 2.5h
  11. morality_law (115) — 2.5h
  12. english (296) — 5h
  13. chinese (209) — 4h
  14. math (337) — 6h
  - **总: ~32h 串行**, 实际上 LLM 跑批可能更快 (串行不卡 30-60min/task)

**每步交付**:
1. bg task 跑完 → merge 到 all_v3.3.json → audit_concepts.py → 修 issue → commit
2. 不跑偏: 跑完跑审查, 看新问题, 修, commit, 再下一学科

**风险**:
- 概念当前 description 质量参差 → LLM 生成 academic_req 质量也参差
- 修法: prompt 加"参考 content_req + description, 写出 1 句学生要会什么的学业要求, 50-100 字"
- 跑 1 概念测试, 看效果, 调 prompt

## P1 — teaching_voice 独立字段 (1 天)

**为什么 P1**: V3.6.9 在 UI 上挂羊头卖狗肉, "🎓 这步怎么教 老师口吻 · 3 句话讲明白" 实际显示的是 description 字段. 用户(老师)用了才发现"哎这不是教学话术啊".

**目标**:
- 1906 概念**全部**生成 teaching_voice 独立字段
- prompt: "老师口吻, 3 句话讲明白, 30-60 字, 含 1 个生活例子, 不要用'理解/培养/掌握'"

**方法**:
- 14 学科串行, 每学科 1 个 bg task
- LLM 一次生成, 30-60 字

**每步**:
- bg task 跑完 → merge → audit 看新 teaching_voice 字段覆盖率 → 修 → commit
- UI 3d.js + funnel.js 把 "teaching_voice 字段" 改回去, 不再复用 description

## P2 — 优质题目库 (6 个月+)

**为什么 P2**: 这是 K12 产品**核心竞争力** (Khan Academy / 学而思 / 猿辅导都靠题库赚钱), 跟"图谱基础设施"分两个赛道. 0 道题 → 没竞争力, 1000 道题 → 试用 OK, 10000 道题 → 商业化.

**目标**:
- 第一阶段 (V4.0): 每个概念配 3-5 道题 (选择/填空/简答), 共 6000-9500 道题
- 题型: 选择 (4 选 1) / 填空 (1-3 关键词) / 简答 (3-5 句)
- 难度 1-5 星 (对齐 difficulty 字段)
- 关联 lineage (题是测"本概念"还是"前置"还是"后置")

**方法** (远期, 先列 TODO):
- 题库架构: data/exercises/v1.json, schema 跟 nodes 对齐
- 题目来源: LLM 生成 + 教材改编 + 公开题库
- 质量审查: audit_exercises.py 跟 audit_concepts.py 对应

**不在 V3.7 范围**: 留到 V4.0 立项做.

## P3 — 审查制度化 (持续)

**为什么 P3**: 审查是"工程纪律", 不是一次性任务. 每次数据更新都要跑, 防止 LLM 引入新错误.

**目标**:
- tools/audit_concepts.py 进 GitHub Actions CI
- 每次 push 自动跑, 报告覆盖率 + 缺字段 Top 30
- 覆盖率掉到 95% 以下, CI 红灯, 阻断 merge

**方法**:
- .github/workflows/audit.yml: schedule (每天) + on push
- 报告输出 PR comment + artifacts

**不在 V3.7 范围**: 留到 V3.7 完成后做.

## 风险与备选

**风险 1**: LLM 生成 academic_req 质量不达预期
- 备选: prompt 加"参考 V3.3 已有的 263 个 academic_req 案例, 模仿语气"
- 备选 2: 跑 1 概念后, 让用户审 5-10 个样本, 调整 prompt 再批量

**风险 2**: Token plan 撞墙 (V3.3.1 教训, 4 个学科失败)
- 备选: 串行 1 个 task 跑, 跑完等, 再开下一个
- 备选 2: 直接在 Mavis session 跑 (不通过 sub-agent, 1 orchestrator 串行)

**风险 3**: 跑批过程中发现其他数据 bug
- 备选: 每个 task 跑完都跑 audit + 修, 不堆积

**不跑偏原则**:
- 每个 commit 都要通过 audit (覆盖率不掉)
- 任何新发现的问题, 立即修, 不留到下一阶段
- 跨学科一致 (prompt 模板统一, 不让 14 学科格式参差)
